会場集計ツール 200人同時回答シミュレーション結果
実施日: 2026-08-25

結論
現状の Google Apps Script + Googleスプレッドシート保存方式では、200人が同時に回答する本番運用は危険です。
20人同時でも半分程度が正常応答できず、200人同時ではほとんどの回答が失敗しました。

実施したテスト
本番の Google Apps Script API に対して、参加者が回答ボタンを押した時と同じ action=answer リクエストを送信しました。
各リクエストは別々の clientId / answerId を使い、同一端末重複扱いにならないようにしています。

見えている原因
- Apps Script側で ScriptLock を使って全リクエストを直列処理している。
- 回答ごとにスプレッドシートを開く、状態JSONを読む、回答行を追加する、状態JSONを書き戻す、という重い処理をしている。
- 各回答レスポンスで history を含む state 全体を返しているため、回答数が増えるほど通信量も増える。
- Google Apps Script / Google Sheets は瞬間的な大量書き込みの受け口としては細い。

現状のまま本番利用する場合のリスク
- QR表示直後に参加者が一斉回答すると、回答が反映されない人が多く出る。
- 参加者側は「送信失敗」または「送信中のまま」に見える可能性がある。
- 進行画面に表示される件数が実際の回答数より少なくなる。
- 60秒回答のような短い受付時間では、200人分を受け切れない可能性が高い。

最低限の回避策
- 回答受付時間を長くする。
- 「一斉に押してください」ではなく、数十秒から2分程度ばらける導線にする。
- 回答失敗時に再送できるUIを入れる。

推奨修正
本番で200人規模を想定するなら、Apps Script + Sheets直書きから変えるのが安全です。
候補:
1. Supabase / Firebase など、同時書き込みに強いDBへ変更する。
2. Apps Scriptを続ける場合でも、回答リクエストではstate全体を更新せず、回答ログ追加だけにする。
3. 進行画面側は定期的に回答ログを集計する方式に変える。
4. 送信失敗時の自動リトライを入れる。
5. 本番前に300件程度で再負荷テストする。
